# Выявление нарушений кассовой дисциплины по видео с камер банка

Решение для ForteBank Datathon 26. Локальный сервис: принимает видео из кассового помещения (`.mov`, 464×848, до ~145 с), возвращает вердикт (`violation` / `no_violation`) и список нарушений с типом, таймкодом, 1–3 кадрами-доказательствами, описанием и ссылкой на пункт нормативного акта РК.

Результат сервиса — **подсказка для проверяющего сотрудника, а не юридический вывод** (ТЗ, п. 7). Все модели работают локально, облачные AI API при обработке не используются. Распознавания лиц и анализа звука нет.

## 1. Адрес сервиса и API

| Параметр | Значение |
|---|---|
| Публичный URL | `https://representations-reserved-kentucky-derby.trycloudflare.com` (Cloudflare quick tunnel к GPU-серверу) |
| Базовый адрес API | `<публичный URL>/api/v1` |
| Веб-интерфейс | `<публичный URL>/?key=<ключ>` (загрузка видео, статус, карточки нарушений; ключ запоминается в браузере, без параметра его можно ввести в форме); `<публичный URL>/#rules` — каталог «Нарушения и источники» |
| Ключ доступа | заголовок `X-API-Key`; значение передаётся жюри в форме сдачи решения, в репозитории не хранится |
| Проверка живости | `GET /health` |

### Контракт API

**1. Отправка видео.** `POST /api/v1/analyze`, `multipart/form-data`, поле `file`, заголовок `X-API-Key`. Ответ содержит `job_id`.

**2. Получение результата.** `GET /api/v1/jobs/{job_id}` (заголовок `X-API-Key`). Поле `status`: `processing` | `done` | `failed`.

**Дополнительно (в ТЗ нет).** `GET /api/v1/jobs/{job_id}/video` — загруженное видео для плеера, с поддержкой `Range`; ключ — заголовок `X-API-Key` или параметр `?key=` (тег `<video>` не умеет передавать заголовки). Если видеокодек не воспроизводится браузерами (HEVC с iPhone, mpeg4, ProRes, 10-битный H.264) или контейнер не MOV/MP4/MKV/WebM, сервер после загрузки в фоне делает копию H.264 `.mp4` (PyAV/libx264, иначе ffmpeg из `imageio-ffmpeg`, если установлен) и отдаёт её как `video/mp4`; анализ всегда идёт по оригиналу и копию не ждёт. Если кодировщика нет, отдаётся оригинал, и интерфейс пишет, что видео не воспроизводится. `GET /api/v1/rules` (ключ так же) — каталог нарушений: `{"rules": [{"id", "type", "summary", "signals", "strength", "norm": {"act", "point", "url", "quote"}}], "sources": [...], "principle": "...", "strengths": {...}, "not_checkable": [...]}`; список правил читается из `app/rules.yaml`, остальное — из `app/norms.yaml`. `GET /api/v1/jobs?limit=50` (ключ так же) — история проверок для интерфейса, новые сверху: `{"jobs": [{"job_id", "filename", "status", "verdict", "n_violations", "submitted_at", "duration_s", "error", "queued"}]}`; `limit` от 1 до 200; читаются только маленькие служебные файлы задачи (`filename`, `submitted_at`, `duration_s`, `summary.json`), кадры-доказательства не загружаются. Отклонённая загрузка (`400`, `413`) задачу не создаёт.

Без заголовка `X-API-Key` или с неверным ключом сервис отвечает `401`. Слишком большой файл — `413` (лимит по умолчанию 300 МБ, переменная `MAX_UPLOAD_MB`), пустой файл — `400`, неизвестный `job_id` — `404`.

```bash
# 1) отправить видео
curl -X POST "$URL/api/v1/analyze" \
  -H "X-API-Key: $API_KEY" \
  -F "file=@video.mov"
# -> {"job_id": "...", "status": "processing"}

# 2) опрашивать, пока status не станет done
curl "$URL/api/v1/jobs/<job_id>" -H "X-API-Key: $API_KEY"
```

Формат результата при `status = done`:

```json
{
  "job_id": "<id задачи>",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Наличные или ценности оставлены без присмотра",
      "timecode_sec": <секунды>,
      "description": "<текст по шаблону правила> Норматив: <акт>, <пункт>.",
      "evidence_frames": [
        {"timestamp_sec": <секунды>, "image_base64": "<JPEG в base64>"}
      ],
      "rule_id": "<id правила>",
      "rule": {"act": "<акт>", "point": "<пункт>", "strength": "<В|С|Н>", "url": "<ссылка на adilet>"},
      "confidence": <0..1>,
      "region": [<x1>, <y1>, <x2>, <y2>]
    }
  ]
}
```

Поля по ТЗ (раздел 10): `job_id`, `status`, `verdict`, `violations[type, timecode_sec, description, evidence_frames[timestamp_sec, image_base64]]`; на каждое нарушение приходит от 1 до 3 кадров JPEG в base64. Поля `rule_id`, `rule`, `confidence`, `region` — **наши дополнительные**, в ТЗ их нет. `region` — зона нарушения на кадре (стол, сейф, дверь или ноутбук, найденные на этом видео) в долях кадра 0..1 от левого верхнего угла; поля нет, если нарушение касается всего кадра или зона не найдена. Для `processing` и `failed` список `violations` в ответ не включается; при `failed` приходит поле `error`. Пример показывает только структуру: значения в угловых скобках — заполнители, это не результат реального прогона (JSON выше не является валидным ответом буквально).

Время обработки: цель — не более 2 минут на видео (лимит жюри — 5 минут). Лимит задачи считается **от момента отправки** (`JOB_LIMIT_S`, по умолчанию 270 с), то есть включает ожидание в очереди: при пакетной отправке нескольких видео у поздних задач остаётся меньше времени. Бюджет анализа одного видео — `min(TIME_BUDGET_S, JOB_LIMIT_S − время с момента отправки − 20 с)`, не меньше 0 (`TIME_BUDGET_S` по умолчанию 200 с). Внутри бюджета: зонды VLM останавливаются на 0,6 бюджета; перепроверка S7 идёт пачками по 8 кандидатов, перед каждой пачкой проверяется время, и после исчерпания бюджета оставшиеся кандидаты принимаются только если они «сильные»; шаг S8 запускается только при расходе менее 0,7 бюджета и имеет свой крайний срок на 0,9 бюджета. Остальные стадии (декодирование, поиск зон, трекинг) прервать нельзя. Сбой VLM на шагах S1 (зоны — значения по умолчанию), S7 (принимаются только «сильные» кандидаты) и S8 (канал пропускается) задачу не роняет; `failed` возможен, если VLM-сервер недоступен на шаге зондов S4 или видео не декодируется. Фактическое время в финальном прогоне всех 42 открытых видео через публичный API (18.10.2026, видео отправлялись по одному, последовательно, как у жюри): в среднем 62 с, медиана 42 с, максимум 152 с (Х-4); все 42 задачи завершились со статусом `done` (подробнее — раздел 8).

## 2. Инструкция запуска

> **Проверка на Windows-ноутбуке с 4–8 ГБ видеопамяти** (меньшая модель через Ollama): см. [docs/windows_laptop.md](docs/windows_laptop.md).

**Запуск одной командой:** Windows — двойной щелчок по `start.bat`, macOS/Linux — `./start.sh` (окружение, зависимости, Ollama и модель настраиваются сами; `demo` — режим без модели), см. [docs/windows_laptop.md](docs/windows_laptop.md#быстрый-запуск).

Целевая платформа — Linux-хост с NVIDIA GPU. Продакшен-сервер, на котором работает публичный адрес: Vast.ai, RTX 3090 24 ГБ; модель `Qwen/Qwen3-VL-8B-Instruct-FP8` на vLLM (`VLM_GPU_UTIL=0.72`), детектор предметов OWLv2 включён (`OBJ_DETECTOR=owlv2`), детектор людей `frcnn_r50v2` на `cuda`. Пошаговая инструкция с командами и разбором типичных проблем — [DEPLOY.md](DEPLOY.md). Кратко:

### Офлайн-режим

`deploy/start.sh` экспортирует `HF_HUB_OFFLINE=1` (и `TRANSFORMERS_OFFLINE=1`), поэтому сервис и vLLM не обращаются к Hugging Face. Все веса — VLM, детектора людей torchvision и OWLv2 — скачиваются заранее в `deploy/setup.sh` и `deploy/enable_owl.sh` (последний после загрузки проверяет, что OWLv2 открывается офлайн). На продакшен-сервере обработка видео идёт в этом офлайн-режиме; интернет нужен только туннелю, через который жюри обращается к сервису.

Очередь — один воркер, видео обрабатываются последовательно. Файлы и результаты хранятся на диске в `JOBS_DIR/{job_id}/`.

## 3. Архитектура

### Принцип

> **Время — из CV, смысл — из VLM, пункт — из каталога.**

1. Таймкоды вычисляются кодом (журнал событий CV и начала интервалов состояний). VLM таймкод не называет.
2. VLM задаются узкие вопросы «да/нет» о фактах на кропе зоны («есть ли на столе банкноты?»), а не открытый вопрос «есть ли нарушение?». Берётся вероятность ответа «Yes» из логитов первого токена.
3. Нарушение = событие + состояние в этот момент. Уход кассира, вход, открытый сейф сами по себе не являются нарушением.
4. Ссылки на пункты НПА берутся только из каталога `app/rules.yaml`; VLM номера пунктов не пишет.
5. Ничего не привязано к конкретному ракурсу: зоны (стол, сейф, дверь, ноутбук) ищутся VLM заново на каждом видео.

### Пайплайн

```
POST /api/v1/analyze -> очередь -> воркер:
 S0 Декодер ......... кадры видео (PyAV), сетка 5 fps для CV и 1 fps для зондов
 S1 Калибровка сцены  зоны: стол, сейф, дверь, ноутбук (VLM grounding, на каждом видео)
 S2 Люди ............ детектор + трекер -> события: «кассир ушёл», «кассир вошёл в пустую комнату», «посетитель вошёл/вышел», роли
 S3 Фильтр изменений  разность кадров в зонах -> «здесь что-то поменялось» (плотные кадры)
 S4 Зонды VLM ....... вопросы да/нет по кропам зон -> P(да)(t)
 S5 Таймлайн ........ сглаживание + пороги -> интервалы состояний
 S6 Правила ......... события x состояния -> кандидаты (правило, t)
 S7 Перепроверка .... клип вокруг кандидата, 2-3 формулировки вопроса, голосование
 S8 Неизвестные типы  «опиши» клип у события + сверка описания с каждым правилом каталога
 S9 Сборщик ......... слияние, вердикт, кадры, описание по шаблону, пункт НПА -> JSON
GET /api/v1/jobs/{job_id} <- результат
```

| Шаг | Что делает | Чем |
|---|---|---|
| S0 | декодирование, время кадра по pts | PyAV |
| S1 | поиск зон на кадре | Qwen3-VL (или Qwen3.5-9B) (grounding) |
| S2 | детекция людей, трекинг, роли без лиц | torchvision Faster R-CNN + ByteTrack (`trackers`, `supervision`) |
| S3 | изменения в зонах | OpenCV |
| S4 | факты `F_*` по кропам, `facts.yaml` | Qwen3-VL (или Qwen3.5-9B) через vLLM |
| S5, S6, S9 | таймлайн, правила, сборка JSON | наш код + `rules.yaml` |
| S7 | перепроверка кандидатов | Qwen3-VL (или Qwen3.5-9B) |
| S8 | поиск нарушений вне основных триггеров | Qwen3-VL (или Qwen3.5-9B) (описание клипа, затем текстовые вопросы да/нет) |

Роли определяются без лиц: кассира выбирает Qwen среди людей, пронумерованных рамками на 1–3 ключевых кадрах, по признакам роли (экран ноутбука повёрнут к нему, сейф и счётная машинка на его стороне; `app/pipeline/roles.py`); если модель не уверена (P < 0,6), кассир — трек, дольше всех находящийся у рабочего места. Порог «ушёл» задан в ростах самого кассира (0,24 высоты его рамки), а не в долях кадра, поэтому не зависит от масштаба и ракурса. Остальные — по поведению. Треки с очень малой высотой относительно кассира (отражения в стеклянной перегородке) отбрасываются.

### S8: нарушения вне основных триггеров

Шаг выполняется, только если он включён (`UNKNOWN_CHANNEL`, по умолчанию включён) и израсходовано менее 70 % бюджета времени. Для не более чем 6 событий CV локальная VLM описывает клип (до 6 кадров, от −2 до +4 с относительно события). Затем для каждого включённого правила каталога, по которому нарушение ещё не найдено, задаётся текстовый вопрос да/нет: «показывает ли описание нарушение правила `<id>: <тип>`?». Если вероятность «да» не ниже 0,85, создаётся кандидат этого правила на время события. Такой кандидат проходит ту же перепроверку S7 по вопросам этого правила (`verify` в `rules.yaml`) и принимается только при её подтверждении: кандидаты S8 никогда не считаются «сильными». Правила без вопросов перепроверки (R08, R18) и правила с `s8: false` в `params` (R16, R22: «без пересчёта» и «сейф открыт с начала пересчёта» по одному клипу не подтвердить) S8 не предлагает. Правила, которые уже предложил CV-путь, S8 повторно не проверяет. Отдельного типа «Иное» (R99) нет: тип и пункт НПА по-прежнему берутся только из `rules.yaml`, VLM их не формулирует.

### Принятие решения

- Кандидат, предложенный CV-путём (S6), принимается, если перепроверка S7 подтвердила его **или** он «сильный»: P(да) зонда ≥ 0,8 на `strong_k` (по умолчанию 3) подряд идущих кадрах базовой сетки зондов (1 кадр/с; плотные дополнительные кадры не считаются). Сигнал берётся из состояния **после** события: для правил «при уходе кассира» (R01–R04, R17) — в окне 5 с после ухода, для R06 — от −1 до +2 с от входа, для правил состояния — от времени кандидата до конца интервала. Поэтому стол, убранный или закрытый перед самым уходом, «сильного» кандидата не даёт, и решение остаётся за S7. Исключение — R04, когда кассир выключил свет и ушёл в течение 4 с: экран в темноте засвечен и зонду не читается, поэтому сигнал берётся из последних 5 с, пока свет ещё горел.
- Попадания S8 принимаются только после подтверждения перепроверкой S7 (см. выше). S8 не трогает правила, уже предложенные CV-путём (в том числе отклонённые перепроверкой).
- Если VLM-сервер отказал во время перепроверки S7, задача не падает: непроверенные кандидаты принимаются только если они «сильные» (в отладочной информации — `verify_error`).
- Одинаковые правила в окне 5 с сливаются; список сортируется по уверенности.
- `verdict = violation`, если принято хотя бы одно нарушение.
- Бюджет времени считается от отправки видео (см. раздел 1): при нехватке времени зонды останавливаются на том, что успели, перепроверка обрывается между пачками, а S8 не запускается; сервис возвращает результат, а не `failed`. `failed` возможен при недоступном VLM-сервере на шаге зондов или недекодируемом видео.
- Кадры-доказательства (1–3 кадра, JPEG в base64, отсортированы по времени): момент события; момент максимальной вероятности зонда в том же окне после события, по которому оценивается «сильность» (для правил без зондов — R05, R09 — момент примерно через 1 с после события); кадр через ~3 с после события.
- Пороги — стартовые значения, подлежат подбору на обучающих видео (см. раздел 7).

### Принцип сопоставления

Каждое правило каталога строится по цепочке «сигнал → факт → правило → пункт норматива → кадры-доказательства».

Часть сигналов дают локальные модели без VLM: детектор и трекер людей (S2) отмечают уход и возвращение кассира, вход и выход посетителей и их число, а пиксельный анализ показывает состояние двери и яркость кадра. VLM задаём только узкие вопросы да/нет о видимом факте по кропу зоны (стол, сейф, дверь, ноутбук или весь кадр): лежат ли банкноты, открыт ли сейф, торчит ли ключ, показывают ли экран посетителю. Ряды P(да) сглаживаются и превращаются в интервалы состояний.

Нарушение — это событие вместе с состоянием в этот момент (кассир ушёл, а наличные на столе; вошёл посетитель, а деньги прошлой операции не убраны), а не само действие: уходы, входы и открытый при клиенте сейф есть и на чистых видео.

Правило привязывается к пункту акта, только если пункт прямо описывает видимое или его назначение однозначно с ним связано. Цитата берётся дословно из docs/normative_research.md, сверенного с adilet.zan.kz.

Кандидата перепроверяет VLM (S7): 2–4 формулировки вопроса по клипу из 6–8 кадров, решение большинством голосов; вопрос о контексте, на котором держится правило (открытая дверца сейфа у R22), обязателен и отклоняет кандидата при любом большинстве. Без подтверждения остаётся только кандидат, у которого факт уверенно держится несколько секунд подряд; для правил с неоднозначными сигналами подтверждение обязательно. Правила по пиксельным сигналам (дверь, яркость кадра) идут без S7.

В отчёт попадают тип, таймкод события, 1–3 кадра (момент события, пик уверенности, кадр через 3 с), описание по шаблону, пункт акта и ссылка на adilet.

Сила связи: В — пункт прямо требует или запрещает то, что видно на кадре; С — пункт прямой, но для вывода нужен контекст (кто человек, какая операция); Н — связь выведена из назначения нормы. Для Н описание начинается с «Возможное несоответствие: »: это подсказка администратору, который проверяет каждый результат, а не юридический вывод.

Типы, которые по видео без звука и без распознавания лиц не отличить от нормы, и типы, которые исследование прямо велит не флагать, вынесены в список непроверяемых с указанием причины.

## 7. Ограничения и известные ошибки

Ниже — пропуски и ложные срабатывания финального прогона 42 открытых видео через публичный API (18.10.2026, метрики — в разделе 8), затем общие ограничения.

**Пропущенные нарушения (вердикт `no_violation` на размеченном видео, 7 из 22)**
- Х-1, 22 с, R20 (возврат части принятых наличных клиенту): правило не сработало.
- Х-2, 10 с, R14 (документ клиента не зафиксирован): R14 по замыслу выводится подсказкой для проверяющего и вердикт не меняет (`hint: true` в `app/rules.yaml`, см. раздел 5 и `app/norms.yaml`), поэтому видео, где размечено только это нарушение, по вердикту не ловится; в этом прогоне подсказки на Х-2 тоже нет.
- Х-15, 15 с, R01: трекер людей так и не выдаёт событие ухода кассира, а R01 срабатывает только от него.
- Х-22, 14 с, R03: ключ в замке сейфа занимает несколько пикселей, зонд его не видит.
- Х-34, 13 с, R13 (пересчёт после ухода клиента): вероятность зонда пересчёта `F_counting` остаётся низкой.
- Х-38, 33 с, R06: зонд наличных на столе `F_cash_desk` не срабатывает.
- Х-44, 16 с: две пачки из счётной машинки не проверены; правила для этого в каталоге нет (см. «Что не проверяется по видео», раздел 6).

**Ошибки времени или типа на пойманных видео**
- Х-18, R09: найдено в 15,6 с при метке 20 с (|Δt| = 4,4 с, тип верный): трекер видит мужчину через стеклянную перегородку ещё до того, как он входит.

**Качество изображения и видимость**
- Детали на уровне рук трудно различимы при разрешении 464×848, поэтому смешение номиналов и выдача без пересчёта не проверяются (см. «Что не проверяется по видео» в разделе 6). Смешение наличных разных операций (R07), уборку наличных в сейф без пересчёта (R16) и деление пачки после пересчёта (R20) правила распознают косвенно — по последовательности событий и состояний (деньги на столе при входе, передача через стол, подход к сейфу), а не по движениям рук.
- Отражения в стеклянной перегородке могут давать «фантомные» треки людей. Они отбрасываются по малой относительной высоте, но полностью исключить такие ошибки нельзя.
- Осмотр пломбы и целостности сумки при инкассации на этом разрешении не виден; R15 опирается на косвенный признак (длительность и отсутствие обмена бумагами).

**Новые ракурсы и планировки**
- Зоны (стол, сейф, дверь, ноутбук) ищет VLM на каждом видео. На новом ракурсе поиск может ошибиться или не найти зону; если стол не найден, используется зона по умолчанию. Правила, зависящие от ненайденной зоны, могут пропускать нарушения или давать ложные.
- Соглашение о координатах при VLM-grounding (`VLM_COORD_MODE`) `deploy/start.sh` определяет при каждом запуске по тестовому кадру (`rel1000` или `abs`; если проверка не удалась — `rel1000`). `deploy/switch_vlm.sh` и `deploy/revert_vlm.sh` перезапускают модель через `start.sh`, поэтому после смены модели формат проверяется заново.

**Принципиальные ограничения**
- Видео обрабатываются по одному: одновременно отправленные задачи встают в очередь. Лимит задачи считается от отправки, поэтому у последних видео пакета бюджет анализа меньше (меньше кадров зондов, перепроверка и S8 короче).
- Камеру мобильного телефона по видео доказать нельзя (п. 12 ч. 2 акта A допускает средства связи без фото- и видеофункции). R11 фиксирует использование телефона, а не наличие камеры.
- Правила силы Н (см. таблицу в разделе 5) — интерпретации норм, а не прямые запреты. Например, явной обязанности блокировать экран при каждом уходе в открытых актах нет; автоблокировка по п. 71 пп. 9) — через 30 минут.
- Контролирующий работник, документ клиента или цифровой документ могли быть вне кадра; для R14 и R15 это возможный источник ложных срабатываний.
- R20 может сработать на законный возврат денег клиенту в рамках операции (например, сдачу или размен), а также на возврат квитанции или документа, если VLM примет их за банкноты. Выдачу наличных из сейфа отсекает второй вопрос перепроверки S7; кандидаты R20 всегда проходят перепроверку. На X-1 (единственный размеченный пример) R20 пока не срабатывает: возврат части купюр на 464×848 модель не отличает от возврата квитанции.
- Результат — подсказка для проверяющего, а не юридический вывод (ТЗ, п. 7). Лица не распознаются, звук не анализируется.

**Калибровка**
- Все правила откалиброваны на 42 открытых видео на production-модели (диагностика ошибок по каждому видео, 17–18.10.2026); R14 по итогам выведен в подсказки (см. раздел 5).
- Пороги (минимальные длительности, число подряд идущих кадров, чувствительность детектора изменений) откалиброваны на 42 открытых видео при диагностике ошибок на продакшен-модели Qwen3-VL-8B-Instruct-FP8 (параметры `params` правил в `rules.yaml`). Текущие значения — в `app/rules.yaml` и `app/facts.yaml`. Калибровка шла на тех же видео, на которых посчитаны метрики раздела 8, поэтому на новых видео качество может быть ниже.
- Остаётся риск несоответствия таймкода: допуск оценки — не более 2 с; в финальном прогоне в него попали 15 из 24 размеченных таймкодов (62,5 %), см. раздел 8.

## 8. Качество на обучающих видео

Таблица — финальный прогон 18.10.2026: все 42 открытых видео отправлены через публичный API продакшен-сервера по одному, последовательно, как это делает жюри; в расчёт идут поля `verdict` и `violations` ответа (подсказки R14 вердикт не меняют и не учитываются). Определения метрик те же, что в функции `score()` скрипта `scripts/eval.py`, который прогоняет пайплайн локально и разбивает метрики по планировкам помещения (`data/layouts.csv`).

Целевые критерии, заявленные в методологии (`docs/methodology.md`): полнота вердикта на видео с нарушениями — 100 %; не более 2 ложных `violation` на чистых видео; |Δt| таймкода не более 2 с для не менее 80 % размеченных нарушений. Это цели; достигнутые значения — в таблице.

| Метрика | Все видео | Планировка A | Планировка B | Планировка C | Планировка D | Планировка E |
|---|---|---|---|---|---|---|
| Полнота вердикта | 15/22 (68 %) | 4/6 (67 %) | 6/8 (75 %) | 2/2 (100 %) | 0/2 (0 %) | 3/4 (75 %) |
| Ложные `violation` на чистых видео | 1/20 | 0/5 | 0/9 | 0/1 | 1/3 | 0/2 |
| Доля таймкодов с \|Δt\| ≤ 2 с | 15/24 (62,5 %) | 5/8 (62,5 %) | 6/8 (75 %) | 1/2 (50 %) | 0/2 (0 %) | 3/4 (75 %) |
| Совпадение типа с разметкой | 15/24 (62,5 %) | 5/8 (62,5 %) | 6/8 (75 %) | 1/2 (50 %) | 0/2 (0 %) | 3/4 (75 %) |

Полнота вердикта — доля видео с размеченным нарушением, получивших `violation`; ложные — число чистых видео с `violation`. Для каждой размеченной метки берётся ближайшее по времени найденное нарушение, и таймкод засчитывается при |Δt| ≤ 2 с. Совпадение типа считается от всех 24 меток, а не только от попавших по времени: метка засчитывается, если ближайшее нарушение попало в ±2 с и его `rule_id` совпадает с типом из `data/types.csv` (из 15 меток, попавших по времени, тип совпал у всех 15). Дубликаты считаются отдельными файлами, как их увидит жюри: Х-47 — тот же ролик, что Х-4, Х-48 — тот же, что Х-5; оба отнесены к планировке A. У ролика Х-4/Х-47 в разметке две метки (57 с у Х-4 и 68 с у Х-47, типы R06 и R07), и обоим файлам приписаны обе; Х-48, как и Х-5, чистое. Поэтому видео с нарушениями 22, чистых 20, меток 24. Разбор каждой ошибки — в разделе 7.

Скрипт `scripts/eval.py` также считает полноту кандидатов `candidate_recall_3s` — долю размеченных нарушений, рядом с которыми (±3 с) был хотя бы один кандидат CV или S8, принятый или нет; это потолок для перепроверки и логики решения. Подробности по каждому кандидату — в `debug.candidates_detail` файла `eval_out/<видео>.json`. В ответе публичного API отладочных данных нет, поэтому для финального прогона эта величина не приводится. Устойчивость к новым ракурсам проверена на синтетических вариантах видео (см. выше): события кассира совпали с оригиналом в 18 из 20 случаев.

Время обработки одного видео в финальном прогоне: в среднем 62 с, медиана 42 с, максимум 152 с (Х-4; его дубликат Х-47 — 151 с). Все 42 задачи уложились в лимит жюри 300 с; цель «не более 2 минут» (раздел 1) превышена на 8 видео из 42 (135–152 с).

**Дополнительная проверка.** Кроме открытого набора использовались:
- 13 собственных тестовых роликов, сгенерированных AI (720×1280, другие сценарии: деньги в карман, фотосъёмка денег, передача третьему лицу, экран показан посетителю, сейф оставлен открытым и др.), каталог `aidataset/` (в git не входит). На них проверялись в том числе типы из списка «Что не проверяется по видео» (раздел 6).
- 20 синтетических вариантов ракурса видео датасета (зеркальное отражение, кадрирование 75 %, уменьшение до 50 %, вписывание в кадр 16:9 с полями, «дальняя камера»): события кассира совпали с исходным видео в 18 из 20 при выборе кассира через Qwen против 13 из 20 со старой эвристикой «дольше всех у стола».
