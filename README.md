# Выявление нарушений кассовой дисциплины по видео с камер банка

Решение для ForteBank Datathon 26. Локальный сервис: принимает видео из кассового помещения (`.mov`, 464×848, до ~145 с), возвращает вердикт (`violation` / `no_violation`) и список нарушений с типом, таймкодом, 1–3 кадрами-доказательствами, описанием и ссылкой на пункт нормативного акта РК.

Результат сервиса — **подсказка для проверяющего сотрудника, а не юридический вывод** (ТЗ, п. 7). Все модели работают локально, облачные AI API при обработке не используются. Распознавания лиц и анализа звука нет.

> Пометка «⏳» в тексте означает значение, которое неизвестно до прогона на GPU-сервере или до развёртывания. Эти места намеренно не заполнены и будут дополнены перед сдачей.

## 1. Адрес сервиса и API

| Параметр | Значение |
|---|---|
| Публичный URL | ⏳ заполнить после развёртывания (публичный адрес туннеля на GPU-сервере) |
| Веб-интерфейс | `<публичный URL>/` (загрузка видео, статус, карточки нарушений) |
| Ключ доступа | заголовок `X-API-Key`; значение передаётся жюри отдельно, в репозитории не хранится |
| Проверка живости | `GET /health` |

### Контракт API

**1. Отправка видео.** `POST /api/v1/analyze`, `multipart/form-data`, поле `file`, заголовок `X-API-Key`. Ответ содержит `job_id`.

**2. Получение результата.** `GET /api/v1/jobs/{job_id}` (заголовок `X-API-Key`). Поле `status`: `processing` | `done` | `failed`.

Без заголовка `X-API-Key` или с неверным ключом сервис отвечает `401`. Слишком большой файл — `413` (лимит по умолчанию 300 МБ, переменная `MAX_UPLOAD_MB`), пустой файл — `400`, неизвестный `job_id` — `404`.

```bash
# 1) отправить видео
curl -X POST "$URL/api/v1/analyze" \
  -H "X-API-Key: $API_KEY" \
  -F "file=@video.mov"
# -> {"job_id": "...", "status": "processing"}

# 2) опрашивать, пока status не станет done
curl "$URL/api/v1/jobs/<job_id>" -H "X-API-Key: $API_KEY"
```

Формат результата при `status = done`:

```json
{
  "job_id": "<id задачи>",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Наличные или ценности оставлены без присмотра",
      "timecode_sec": <секунды>,
      "description": "<текст по шаблону правила> Норматив: <акт>, <пункт>.",
      "evidence_frames": [
        {"timestamp_sec": <секунды>, "image_base64": "<JPEG в base64>"}
      ],
      "rule_id": "<id правила>",
      "rule": {"act": "<акт>", "point": "<пункт>", "strength": "<В|С|Н>", "url": "<ссылка на adilet>"},
      "confidence": <0..1>
    }
  ]
}
```

Поля по ТЗ (раздел 10): `job_id`, `status`, `verdict`, `violations[type, timecode_sec, description, evidence_frames[timestamp_sec, image_base64]]`; на каждое нарушение приходит от 1 до 3 кадров JPEG в base64. Поля `rule_id`, `rule`, `confidence` — **наши дополнительные**, в ТЗ их нет. Для `processing` и `failed` список `violations` в ответ не включается; при `failed` приходит поле `error`. Пример показывает только структуру: значения в угловых скобках — заполнители, это не результат реального прогона (JSON выше не является валидным ответом буквально).

Время обработки: цель — не более 2 минут на видео (лимит жюри — 5 минут). Лимит задачи считается **от момента отправки** (`JOB_LIMIT_S`, по умолчанию 270 с), то есть включает ожидание в очереди: при пакетной отправке нескольких видео у поздних задач остаётся меньше времени. Бюджет анализа одного видео — `min(TIME_BUDGET_S, JOB_LIMIT_S − время с момента отправки − 20 с)`, не меньше 0 (`TIME_BUDGET_S` по умолчанию 200 с). Внутри бюджета: зонды VLM останавливаются на 0,6 бюджета; перепроверка S7 идёт пачками по 8 кандидатов, перед каждой пачкой проверяется время, и после исчерпания бюджета оставшиеся кандидаты принимаются только если они «сильные»; шаг S8 запускается только при расходе менее 0,7 бюджета и имеет свой крайний срок на 0,9 бюджета. Остальные стадии (декодирование, поиск зон, трекинг) прервать нельзя. Сбой VLM на шагах S1 (зоны — значения по умолчанию), S7 (принимаются только «сильные» кандидаты) и S8 (канал пропускается) задачу не роняет; `failed` возможен, если VLM-сервер недоступен на шаге зондов S4 или видео не декодируется. ⏳ фактическое время на видео — заполнить после прогона на GPU (`scripts/eval.py`).

После загрузки весов запуск выполняется с `HF_HUB_OFFLINE=1`. Веса детектора torchvision тоже должны быть загружены заранее (на этапе `setup.sh`), иначе первый запуск попытается скачать их из сети. ⏳ подтвердить на хосте, что обработка видео проходит без исходящего трафика.

Очередь — один воркер, видео обрабатываются последовательно. Файлы и результаты хранятся на диске в `JOBS_DIR/{job_id}/`.

## 3. Архитектура

### Принцип

> **Время — из CV, смысл — из VLM, пункт — из каталога.**

1. Таймкоды вычисляются кодом (журнал событий CV и начала интервалов состояний). VLM таймкод не называет.
2. VLM задаются узкие вопросы «да/нет» о фактах на кропе зоны («есть ли на столе банкноты?»), а не открытый вопрос «есть ли нарушение?». Берётся вероятность ответа «Yes» из логитов первого токена.
3. Нарушение = событие + состояние в этот момент. Уход кассира, вход, открытый сейф сами по себе не являются нарушением.
4. Ссылки на пункты НПА берутся только из каталога `app/rules.yaml`; VLM номера пунктов не пишет.
5. Ничего не привязано к конкретному ракурсу: зоны (стол, сейф, дверь, ноутбук) ищутся VLM заново на каждом видео.

### Пайплайн

```
POST /api/v1/analyze -> очередь -> воркер:
 S0 Декодер ......... кадры видео (PyAV), сетка 5 fps для CV и 1 fps для зондов
 S1 Калибровка сцены  зоны: стол, сейф, дверь, ноутбук (VLM grounding, на каждом видео)
 S2 Люди ............ детектор + трекер -> события: «кассир ушёл», «кассир вошёл в пустую комнату», «посетитель вошёл/вышел», роли
 S3 Фильтр изменений  разность кадров в зонах -> «здесь что-то поменялось» (плотные кадры)
 S4 Зонды VLM ....... вопросы да/нет по кропам зон -> P(да)(t)
 S5 Таймлайн ........ сглаживание + пороги -> интервалы состояний
 S6 Правила ......... события x состояния -> кандидаты (правило, t)
 S7 Перепроверка .... клип вокруг кандидата, 2-3 формулировки вопроса, голосование
 S8 Неизвестные типы  «опиши» клип у события + сверка описания с каждым правилом каталога
 S9 Сборщик ......... слияние, вердикт, кадры, описание по шаблону, пункт НПА -> JSON
GET /api/v1/jobs/{job_id} <- результат
```

| Шаг | Что делает | Чем |
|---|---|---|
| S0 | декодирование, время кадра по pts | PyAV |
| S1 | поиск зон на кадре | Qwen3-VL (grounding) |
| S2 | детекция людей, трекинг, роли без лиц | torchvision Faster R-CNN + ByteTrack (`trackers`, `supervision`) |
| S3 | изменения в зонах | OpenCV |
| S4 | факты `F_*` по кропам, `facts.yaml` | Qwen3-VL через vLLM |
| S5, S6, S9 | таймлайн, правила, сборка JSON | наш код + `rules.yaml` |
| S7 | перепроверка кандидатов | Qwen3-VL |
| S8 | поиск нарушений вне основных триггеров | Qwen3-VL (описание клипа, затем текстовые вопросы да/нет) |

Роли определяются без лиц: кассир — трек, дольше всех находящийся у рабочего места; остальные — по поведению. Треки с очень малой высотой относительно кассира (отражения в стеклянной перегородке) отбрасываются.

### S8: нарушения вне основных триггеров

Шаг выполняется, только если он включён (`UNKNOWN_CHANNEL`, по умолчанию включён) и израсходовано менее 70 % бюджета времени. Для не более чем 6 событий CV локальная VLM описывает клип (до 6 кадров, от −2 до +4 с относительно события). Затем для каждого включённого правила каталога, по которому нарушение ещё не найдено, задаётся текстовый вопрос да/нет: «показывает ли описание нарушение правила `<id>: <тип>`?». Если вероятность «да» не ниже 0,85, создаётся кандидат этого правила на время события. Такой кандидат проходит ту же перепроверку S7 по вопросам этого правила (`verify` в `rules.yaml`) и принимается только при её подтверждении: кандидаты S8 никогда не считаются «сильными». Если у правила нет вопросов перепроверки, попадание S8 сохраняется. Правила, которые уже предложил CV-путь, S8 повторно не проверяет. Отдельного типа «Иное» (R99) нет: тип и пункт НПА по-прежнему берутся только из `rules.yaml`, VLM их не формулирует.

### Принятие решения

- Кандидат, предложенный CV-путём (S6), принимается, если перепроверка S7 подтвердила его **или** он «сильный»: P(да) зонда ≥ 0,8 на `strong_k` (по умолчанию 3) подряд идущих кадрах базовой сетки зондов (1 кадр/с; плотные дополнительные кадры не считаются). Сигнал берётся из состояния **после** события: для правил «при уходе кассира» (R01–R04, R17) — в окне 5 с после ухода, для R06 — от −1 до +2 с от входа, для правил состояния — от времени кандидата до конца интервала. Поэтому стол, убранный или закрытый перед самым уходом, «сильного» кандидата не даёт, и решение остаётся за S7.
- Попадания S8 принимаются только после подтверждения перепроверкой S7 (см. выше). S8 не трогает правила, уже предложенные CV-путём (в том числе отклонённые перепроверкой).
- Если VLM-сервер отказал во время перепроверки S7, задача не падает: непроверенные кандидаты принимаются только если они «сильные» (в отладочной информации — `verify_error`).
- Одинаковые правила в окне 5 с сливаются; список сортируется по уверенности.
- `verdict = violation`, если принято хотя бы одно нарушение.
- Бюджет времени считается от отправки видео (см. раздел 1): при нехватке времени зонды останавливаются на том, что успели, перепроверка обрывается между пачками, а S8 не запускается; сервис возвращает результат, а не `failed`. `failed` возможен при недоступном VLM-сервере на шаге зондов или недекодируемом видео.
- Кадры-доказательства (1–3 кадра, JPEG в base64, отсортированы по времени): момент события; момент максимальной вероятности зонда в том же окне после события, по которому оценивается «сильность» (для правил без зондов — R05, R09 — момент примерно через 1 с после события); кадр через ~3 с после события.
- Пороги — стартовые значения, подлежат подбору на обучающих видео (см. раздел 7).

## 5. Нормативные источники и сопоставление

|---|---|---|

| **B** | Правила организации охраны и устройства помещений БВУ… (пост. Правления НБРК от 24.02.2020 № 14), «Правила № 14» | https://adilet.zan.kz/rus/docs/V2000020075 |
| **G** | Требования к обеспечению информационной безопасности банков… (пост. Правления АРРФР от 03.04.2026 № 53), «АРРФР № 53» | https://adilet.zan.kz/rus/docs/V2600038336 |

Основной источник — акт А: почти все визуально проверяемые требования к кассиру содержатся в нём. Акт B задаёт требования к устройству помещения кассы (дверь на замке, видеокамеры). Акт G — слабая опора для одного типа (незаблокированный ноутбук). Утратившие силу акты не цитируются.

### Сила связи

- **В** — пункт прямо описывает наблюдаемое.
- **С** — пункт прямой, но для вывода нужен контекст (кто человек, какая операция, что было вне кадра).
- **Н** — связь выведена из назначения нормы, то есть это интерпретация. Описания таких нарушений в ответе начинаются словами **«Возможное несоответствие»**.

## 7. Ограничения и известные ошибки

Это результат разработки по состоянию на момент написания; точные списки пропусков и ложных срабатываний будут добавлены по итогам прогона на GPU (⏳ заполнить после прогона `scripts/eval.py`: список пропущенных меток и ложных срабатываний с причиной).

**Качество изображения и видимость**
- Детали на уровне рук трудно различимы при разрешении 464×848: смешение номиналов, выдача без пересчёта, смешение наличных разных операций. Поэтому правила R07, R16 и R19 не реализованы, а смешение номиналов отложено. Деление пачки после пересчёта R20 распознаёт косвенно — по направлению передачи денег через стол (клиент → кассир, пересчёт, кассир → клиент), а не по движениям рук.
- Отражения в стеклянной перегородке могут давать «фантомные» треки людей. Они отбрасываются по малой относительной высоте, но полностью исключить такие ошибки нельзя.
- Осмотр пломбы и целостности сумки при инкассации на этом разрешении не виден; R15 опирается на косвенный признак (длительность и отсутствие обмена бумагами).

**Новые ракурсы и планировки**
- Зоны (стол, сейф, дверь, ноутбук) ищет VLM на каждом видео. На новом ракурсе поиск может ошибиться или не найти зону; если стол не найден, используется зона по умолчанию. Правила, зависящие от ненайденной зоны, могут пропускать нарушения или давать ложные.
- Соглашение о координатах при VLM-grounding (`VLM_COORD_MODE`) подтверждается на GPU-хосте (`scripts/check_grounding.py`); до этого используется значение по умолчанию `rel1000`.

**Принципиальные ограничения**
- Видео обрабатываются по одному: одновременно отправленные задачи встают в очередь. Лимит задачи считается от отправки, поэтому у последних видео пакета бюджет анализа меньше (меньше кадров зондов, перепроверка и S8 короче).
- Камеру мобильного телефона по видео доказать нельзя (п. 12 ч. 2 акта А допускает средства связи без фото- и видеофункции). R11 фиксирует использование телефона, а не наличие камеры.
- Правила силы Н (R04, R08, R09, R12, R18, R20) — интерпретации норм, а не прямые запреты. Например, явной обязанности блокировать экран при каждом уходе в открытых актах нет; автоблокировка по п. 71 пп. 9) — через 30 минут.
- Контролирующий работник, документ клиента или цифровой документ могли быть вне кадра; для R14 и R15 это возможный источник ложных срабатываний.
- R20 может сработать на законный возврат денег клиенту в рамках операции (например, сдачу или размен), а также на возврат квитанции или документа, если VLM примет их за банкноты. Выдачу наличных из сейфа должен отсекать второй вопрос перепроверки S7 (не проверено на GPU); кандидаты R20 всегда проходят перепроверку.
- Результат — подсказка для проверяющего, а не юридический вывод (ТЗ, п. 7). Лица не распознаются, звук не анализируется.

**Калибровка (в процессе)**
- Правила второго уровня R13–R15 и R20 ожидают калибровки по ложным срабатываниям и могут быть отключены или ужесточены по её итогам.
- Пороги (минимальные длительности, число подряд идущих кадров, чувствительность детектора изменений) пока стартовые и подлежат калибровке на 42 обучающих видео. ⏳ итоговые значения порогов — после прогона на GPU.
- Остаётся риск несоответствия таймкода: допуск оценки — не более 2 с, фактическая доля попаданий ⏳ будет определена по `scripts/eval.py`.

## 8. Качество на обучающих видео

Метрики считаются скриптом `scripts/eval.py` на обучающих видео (42 файла, из них 40 уникальных) и разбиваются по планировкам помещения.

Целевые критерии, заявленные в методологии (`docs/methodology.md`): полнота вердикта на видео с нарушениями — 100 %; не более 2 ложных `violation` на чистых видео; |Δt| таймкода не более 2 с для не менее 80 % размеченных нарушений. Это цели, а не достигнутые значения.

| Метрика | Все видео | Планировка A | Планировка B | Планировка C | Планировка D | Планировка E |
|---|---|---|---|---|---|---|
| Полнота вердикта | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ |
| Ложные `violation` на чистых видео | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ |
| Доля таймкодов с \|Δt\| ≤ 2 с | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ |
| Совпадение типа с разметкой | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ | ⏳ |

⏳ заполнить после прогона на GPU (`scripts/eval.py`, JSON с метриками по планировкам). Скрипт также считает полноту кандидатов `candidate_recall_3s` — долю размеченных нарушений, рядом с которыми (±3 с) был хотя бы один кандидат CV или S8, принятый или нет; это потолок для перепроверки и логики решения. Подробности по каждому кандидату — в `debug.candidates_detail` файла `eval_out/<видео>.json`. Отдельно планируется проверка «по планировке»: настройка порогов на части планировок и проверка на остальных (имитация нового ракурса).
