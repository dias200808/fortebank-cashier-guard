# Архитектура: сервис выявления нарушений кассовой дисциплины по видео

Дата: 2026-10-17 · Дедлайн сдачи: 18.10.2026 12:00 · Основа: план команды + поправки по `docs/research_*.md`.

## 1. Цель и критерии успеха

Сервис принимает `.mov` (464×848, ≤145 с), за ≤2 мин возвращает вердикт и список нарушений (тип, таймкод, 1–3 кадра, описание, пункт НПА РК). Работает полностью локально, публичный URL + API с `X-API-Key` (схема из ТЗ, раздел 10).

Успех на 42 обучающих видео (40 уникальных):
- полнота вердикта на 21 видео с нарушениями = 100 %;
- ложные `violation` на 19 чистых — ≤ 2;
- |Δt| таймкода ≤ 2 с для ≥ 80 % размеченных нарушений;
- та же полнота при проверке «по планировке» (настройка на двух планировках, проверка на третьей).

## 2. Принципы

1. **Время даёт код, смысл даёт VLM.** VLM не называет таймкод (Charades-STA: 39–48 mIoU у 7–8B), время берём из журнала CV.
2. **VLM задаём узкие вопросы да/нет о фактах**, а не «есть ли нарушение?» (открытый вопрос: полнота 6 %, декомпозиция: 64 %).
3. **Нарушение = событие + состояние в этот момент.** Уход, вход, открытый сейф сами по себе — норма.
4. **Ссылки на НПА только из каталога** (`rules.yaml`), модель их не генерирует.
5. **Recall первым:** широкая сетка кандидатов, ложные режет перепроверка; пороги подбираются на данных.
6. **Ничего не захардкожено под ракурс:** зоны находятся на каждом видео заново.

## 3. Пайплайн

```
POST /analyze → очередь → воркер:
 S0 Декодер ─ кадры 30 fps (поток), 5 fps (CV), 1 fps (зонды)
 S1 Калибровка сцены ─ зоны: стол, сейф, дверь, ноутбук, рабочее место
 S2 Люди ─ детектор + трекер → события: вход/выход, кассир ушёл/вернулся, роли
 S3 Фильтр изменений ─ разность кадров в зонах (каждый кадр) → «здесь что-то поменялось»
 S4 Зонды VLM ─ вопросы да/нет по кропам зон (1 fps + кадры с изменениями) → P(да)(t)
 S5 Таймлайн ─ сглаживание + пороги → состояния по времени
 S6 Правила ─ события × состояния → кандидаты (тип, t)
 S7 Перепроверка ─ клип ±3 с, 5 fps, кроп, 2–3 формулировки, голосование
 S8 Неизвестные типы ─ на событиях: «опиши» → сверка описания с каждым правилом каталога
 S9 Сборщик ─ слияние, вердикт, кадры, описание по шаблону, пункт НПА → JSON
GET /jobs/{id} ← результат
```

Свой детектор денег — опционально, если зонды S4 плохо видят пачки.

### S2. Роли без лиц
- **Кассир:** трек с наибольшим временем в зоне рабочего места (первый, кто туда сел, если в начале никого нет).
- **Клиент:** сидит/стоит у стола с противоположной стороны.
- **Инкассатор:** вошёл с сумкой или унёс сумку.
- **Посторонний:** любой другой вошедший.
- **Отражения в стекле:** треки с медианной высотой < 0,5 высоты кассира отбрасываются (замер 17.10: отражения 0,06–0,09 кадра, люди в комнате 0,13–0,23).
- **«Кассир ушёл»** = цепочка отходов от места (разрывы ≤ 3 с), которая заканчивается исчезновением кассира; таймкод — начало цепочки (момент, когда встал). Отход к зоне сейфа уходом не считается. Простой «далеко от места» срабатывает на 1–4 с позже метки.
- **Вход/выход** посетителя — начало/конец его трека не у края ролика.

### S3. Быстрые события между секундами и действия руками
- Если в зоне стола/сейфа/двери изменение между двумя секундными зондами (люди замаскированы), S4 дополнительно опрашивает кадры этого промежутка (шаг 0,2 с). Так ловится «деньги исчезли за долю секунды».
- Второй сигнал — активность в зоне стола **без** маскировки людей: передача денег/документа руками не даёт ни событий трекера, ни изменений сцены (замер: X-1, X-2, X-4@68, X-18). По нему тоже добавляются плотные кадры, а факт `F_handover` спрашивается у VLM.

### Почему VLM смотрит всё видео, а не только кандидатов (замер 17.10, 40 видео)
- Сырые события трекера: 21/22 метки в ±3 с, но покрывают ~90 % времени — фильтром не являются.
- Осмысленные события (уход кассира, вход/выход, изменения сцены): 18/22 при покрытии 62–76 %; пропуски — действия руками и напиток (X-1, X-2, X-4@68, X-46), которые видит только VLM.
- Вывод: события CV дают точное время, а полноту даёт сплошной опрос фактов VLM (1 fps + плотные кадры у изменений).

## 6. Протокол VLM

- **Зонд (S4):** один кадр-кроп + вопрос «… Answer Yes or No.» → берём P(Yes) из логитов первого токена, без генерации. Изображение кодируется один раз на кадр, вопросы идут с общим префиксом (prefix caching).
- **Перепроверка (S7):** 6–8 кадров (t−3…t+5 с), кроп зоны + полный кадр, факты из журнала текстом («человек №1 — кассир — покинул кадр в 9,4 с»). 2–3 формулировки вопроса, решение большинством. Без меток/рамок на кадрах (Set-of-Mark малым моделям не помогает).
- **Неизвестные типы (S8):** на событиях S2/S3 — «Опиши, что делают люди и что меняется» → второй текстовый запрос: для каждого правила каталога «нарушено ли? да/нет + цитата из описания». Вход в ответ только при P ≥ высокого порога.
- **Ответы строго в JSON**, парсинг с fallback (повтор с понижением температуры → «не подтверждено»).

## 7. Таймкод и кадры

- Таймкод = время события из S2 (уход/вход/передача) или начало состояния из S5, со смещением, откалиброванным по 22 меткам.
- Бездействие («не закрыл до ухода») — таймкод на момент ухода.
- Кадры: (1) момент события, (2) кадр с макс. P(да) в окне, (3) кадр «после» (подтверждение, что состояние держится). Без лишних рамок; опционально рамка на ключевой зоне.

## 8. Решение и вердикт

- Кандидат принят, если S7 подтвердил (≥2 из 3) **или** P(да) зонда ≥ τ_high на ≥ k кадрах подряд.
- Одинаковые типы в окне 5 с сливаются. Сортировка по уверенности.
- `verdict = violation`, если есть хотя бы одно принятое нарушение.
- Пороги τ, T_door, T_bag, k подбираются на обучающих видео: сначала полнота 100 %, затем минимум ложных. Стартовые значения: τ_high = 0,8, k = 3 кадра, N = 3 с, T_door = 8 с, T_bag = 10 с, T (вещи/телефон/чашка) = 2 с.

## 9. Сервис

- **FastAPI:** `POST /api/v1/analyze` (поле `file`, `.mov`, до 100 МБ) → `job_id`; `GET /api/v1/jobs/{id}` → `processing|done|failed` + результат. `X-API-Key` обязателен, без него 401.
- **Очередь:** один GPU-воркер, задачи последовательно; 5 видео одновременно укладываются при ≤ 1 мин на видео. Таймаут задачи 4 мин → `done` с тем, что успели (не `failed`).
- **Хранение:** файл и результат на диске (`jobs/{id}/`), без БД.
- **UI:** одна страница: загрузка → статус → вердикт, карточки нарушений (тип, таймкод, кадры, описание, пункт НПА, ссылка на adilet).
- **Деплой:** `deploy/setup.sh` + `deploy/start.sh` (инстанс Vast.ai уже контейнер), веса в одной папке, `HF_HUB_OFFLINE=1`; публичный URL через Cloudflare Tunnel (именованный). Демонстрация офлайна: исходящий трафик закрыт файрволом.
- **Железо:** арендованная RTX 3090 24 ГБ (прод) — влезает Qwen3-VL-8B + детекторы и запас под 5 видео; ноутбук с RTX 5060 8 ГБ — разработка (Qwen3-VL-4B в 4 бит).

## 11. Проверка качества

- `eval.py` прогоняет все видео, считает: полноту и ложные по вердикту, |Δt| до ближайшего предсказанного нарушения, совпадение типа с нашей ручной разметкой типов (`docs/dataset_analysis.md`).
- Дубликаты Х-4/Х-47, Х-5/Х-48 — одно видео с двумя метками.
- **По планировке:** настройка порогов на двух планировках, проверка на третьей (имитация нового ракурса).
- Отдельно меряем полноту сетки кандидатов S2+S3+S6 (кандидат в ±3 с от метки) — она должна быть 100 % до подключения VLM.
- Свои 3–5 роликов: новые типы (R05, R18, R19) и новый ракурс.
- Разбор каждой ошибки по слою: сцена / факт / событие / правило / VLM.
